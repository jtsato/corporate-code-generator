# Generated Java Reference Architecture

This document describes the architecture of Java applications generated by the Java Golden Path. It is not the architecture of the generator itself. Current profile versions, Java version, artifact counts, dry-run counts, scripts, tests, smokes, and CI inventory are centralized in [Current State](../project/CURRENT-STATE.md).

The normative capability vocabulary is maintained in [Capability Taxonomy](CAPABILITY-TAXONOMY.md). Decisions and rationale are recorded in the [ADR index](../adr/README.md).

## Scope

The current generated Java application is a Clean Architecture Spring application. The multi-module Golden Path separates domain/application policy from REST representation, persistence infrastructure, and Spring composition.

The current reference entity is `Wallet`, but the architecture is generated from the application model rather than hardcoded as a Wallet-only design.

## Maven modules

| Module | Responsibility | Dependency rule |
| --- | --- | --- |
| `build` | Reactor and shared build configuration. | Does not own application runtime code. |
| `core` | Domain model, commands, use cases, ports, common paging/filter/sorting model, application exceptions, and self-validation. | Must remain Spring-free, JPA-free, REST-free, and infrastructure-free. |
| `entrypoints-rest` | HTTP controllers, request/response DTOs, REST filter/sort parsing, OpenAPI-facing annotations, and REST error representation. | Depends inward on Core contracts and does not depend on persistence implementation. |
| `infra-database` | Spring Data JPA entities, repositories, persistence mappers, Querydsl mapping, paging adapters, and gateway providers. | Implements Core ports and depends inward on Core. |
| `configuration` | Spring Boot application composition, bean wiring, environment configuration, CORS, OpenAPI configuration, architecture tests, and runtime/integration tests. | Composes all runtime modules and owns framework bootstrapping. |

Dependency direction:

```text
configuration
  -> entrypoints-rest -> core
  -> infra-database  -> core

build
  -> reactor/build metadata
```

Core must not depend on `entrypoints-rest`, `infra-database`, or `configuration`.

## Runtime flows

### Collection read, filtering, paging, and sorting

`GET /wallets` returns a domain-specific page response with `items`, `page`, `size`, `totalItems`, and `totalPages`.

The generated flow is:

```text
HTTP query parameters
  -> REST filter/sort/page parsing
  -> FilterExpression + PageRequest + SortOrder
  -> Find<Entity>ByFilterPageUseCase
  -> <Entity>Gateway.findByFilterPage
  -> QuerydslFilterMapper + SpringDataPageRequestMapper
  -> Spring Data repository
  -> SpringDataPageResultMapper
  -> REST response DTO
```

Empty filters fall back to the generated unfiltered repository path. Sorting uses an allowlist generated from entity attributes and maps public REST fields to persistence properties.

Relevant decisions: [ADR-033](../adr/ADR-033-core-filter-common.md), [ADR-034](../adr/ADR-034-rest-filter-contract-foundation.md), [ADR-035](../adr/ADR-035-querydsl-filter-mapper-foundation.md), [ADR-036](../adr/ADR-036-querydsl-filter-runtime-integration.md), [ADR-037](../adr/ADR-037-rest-filter-runtime-integration.md), [ADR-038](../adr/ADR-038-paging-runtime-integration.md), [ADR-039](../adr/ADR-039-filtered-paging-runtime-integration.md), [ADR-040](../adr/ADR-040-rest-filtered-paging-runtime-integration.md), and [ADR-041](../adr/ADR-041-rest-sorting-runtime-integration.md).

### Find by ID

`GET /wallets/{id}` delegates to `Find<Entity>ByIdUseCase`. Existing identifiers return a response DTO. Unknown identifiers map to a not-found error. Malformed identifiers are rejected as bad requests by the generated REST/framework path.

Relevant decision: [ADR-042](../adr/ADR-042-find-by-id-runtime-and-rest-integration.md).

### Create

`POST /wallets` receives a generated request DTO and converts it to `Create<Entity>Command`. The Core create use case delegates to the gateway. The persistence provider checks for duplicate identifiers before saving and maps conflicts to the standard REST error path.

The REST create path returns `201 Created`, a relative `Location`, and the generated response DTO when creation succeeds.

Relevant decisions: [ADR-043](../adr/ADR-043-create-runtime-integration.md), [ADR-044](../adr/ADR-044-create-conflict-runtime-integration.md), and [ADR-046](../adr/ADR-046-rest-create-integration.md).

### Update

`PUT /wallets/{id}` is a full replacement update. The identifier comes from the path, not the body. The generated request DTO converts to `Update<Entity>Command`, delegates to `Update<Entity>UseCase`, and returns the updated response DTO.

Missing identifiers map to not found. Invalid JSON, invalid body values, null values for required fields, and malformed path identifiers map to bad request. Partial updates are exposed through `PATCH /wallets/{id}` in the Java multi-module profile; its mutable request setters distinguish omitted fields from explicit `null`. ETags, conditional requests, and optimistic locking are not part of the current generated behavior.

Relevant decisions: [ADR-047](../adr/ADR-047-update-runtime-integration.md) and [ADR-048](../adr/ADR-048-rest-update-integration.md).

The PATCH interactor loads the current entity, merges only supplied fields, and
calls the existing update gateway operation. Required supplied-null and empty
patches are rejected, while optional supplied-null clears the field. It returns
`200 OK` with the updated response DTO; the single-module profile remains
unchanged.

Relevant decision: [ADR-051](../adr/ADR-051-rest-patch-integration.md).

### Delete

The Core delete contract is implemented and exposed over HTTP. `Delete<Entity>Command` delegates to `Delete<Entity>UseCase`, which calls the gateway. The persistence provider loads the active JPA entity, sets `deletedAt`, changes its `deletionScope` to the identifier string, and saves the row. The row remains physically present while normal reads treat it as absent.

`DELETE /wallets/{id}` receives the typed path identifier, constructs `Delete<Entity>Command(id)` inline in the controller, and delegates to `Delete<Entity>UseCase.execute(...)`. There is no request DTO because an empty body has no representation.

| Condition | Status | Body |
| --- | --- | --- |
| Identifier exists, row soft-deleted | 204 No Content | empty |
| Identifier absent (never existed, or already deleted) | 404 Not Found | `ResponseStatus` |
| Path value not a valid identifier | 400 Bad Request | `ResponseStatus` |
| Unexpected failure | 500 Internal Server Error | `ResponseStatus` |

Delete is **not** idempotent: a repeated `DELETE` on the same identifier returns 404 rather than 204, because the persistence provider maps a missing identifier to the generated not-found contract. This is a deliberate consequence of reusing the accepted delete runtime rather than a defect.

The persistence adapter applies `deleted_at IS NULL AND deletion_scope = ACTIVE` to collection, filter, and paging queries. Find-by-id, update, PATCH, and repeated delete also reject tombstones. An attribute marked `unique: true` receives a composite constraint with `deletion_scope`, so its value can be reused by a new active row after soft deletion without changing the tombstone's business fields. An entity `uniqueGroups` declaration receives the same treatment: every declared tuple becomes a deterministic composite constraint over its business columns plus `deletion_scope`, and the gateway checks the tuple against active rows before create, update, and restore.

Relevant decisions: [ADR-049](../adr/ADR-049-delete-runtime-integration.md), [ADR-050](../adr/ADR-050-rest-delete-integration.md), [ADR-052](../adr/ADR-052-soft-delete-active-uniqueness.md), and [ADR-054](../adr/ADR-054-composite-unique-groups.md).

### Deleted queries and restore

The Java multi-module profile exposes deleted records through explicit routes rather than an `includeDeleted` flag. `GET /wallets/deleted` applies the normal filter, paging, and sorting contract to tombstones only, while `GET /wallets/deleted/{id}` retrieves one tombstone. Tombstone responses contain the business fields and `deletedAt`; normal domain responses remain unchanged.

`POST /wallets/{id}/restore` is a command endpoint that returns 204 with an empty body. Restoring an unknown identifier or an already active row returns 404/409 respectively. If restoring would collide with an active row's attribute-level unique value, the operation returns 409 and the tombstone remains deleted. The generated Core gateway and use cases keep deleted reads and restore separate from active-only reads and writes.

Relevant decision: [ADR-053](../adr/ADR-053-restore-include-deleted-queries.md).

## REST contracts

The generated REST entrypoint owns HTTP representation:

- request DTOs;
- response DTOs;
- page response DTOs;
- REST filter parser;
- REST sort parser;
- controller methods;
- OpenAPI annotations where the OpenAPI capability applies;
- `ResponseStatus` error body representation.

Core exceptions remain technology-neutral. The REST layer and global handler translate them into HTTP responses.

## Persistence

The generated database infrastructure owns:

- JPA entities;
- Spring Data repositories;
- persistence mappers;
- gateway providers implementing Core ports;
- Spring Data paging adapters;
- Querydsl predicate mapping;
- H2-backed tests where generated runtime behavior requires database validation.

The Core owns ports and use cases; infrastructure implements those ports. Persistence annotations and Spring Data types must not leak into Core.

## Validation

Core self-validation is generated for required domain values using Jakarta Validation boundaries. The Core may depend on stable Jakarta API contracts, but it must not depend on Spring or provider-specific validation implementations.

REST request validation and conversion errors are surfaced through the REST/framework path and the generated global error handler. Generated validation behavior must remain deterministic and covered by focused smoke tests when output changes.

Relevant decision: [ADR-028](../adr/ADR-028-jakarta-validation-and-self-validating-in-core.md).

## Errors and i18n

The generated REST error body is `ResponseStatus`, with deterministic fields for status code, message, and field-level errors. Core exceptions carry stable message keys and default messages. Message bundles provide at least the documented baseline locales, and `Accept-Language` drives message resolution with fallback.

Relevant decision: [ADR-025](../adr/ADR-025-standard-rest-error-contract-and-i18n-foundation.md).

## CORS and configuration

The generated configuration module owns environment-specific application configuration and CORS wiring. CORS is property-driven and must not rely on unsafe hardcoded production defaults. Production requires explicit allowed origins.

Relevant decision: [ADR-026](../adr/ADR-026-configuration-profiles-and-cors-policy.md).

## OpenAPI and Swagger UI

The generated application exposes the OpenAPI specification at the documented API-docs path. Swagger UI is environment-gated: local/test may enable it, while base and production configuration disable it by default.

Relevant decision: [ADR-027](../adr/ADR-027-openapi-specification-and-swagger-ui-policy.md).

## Architecture tests

Generated ArchUnit tests live in the configuration module and validate production-code boundaries for the generated multi-module architecture. These tests are Golden Path-specific guardrails; they are not generic generator architecture tests.

Relevant decision: [ADR-024](../adr/ADR-024-archunit-as-default-architecture-guardrail.md).

## Limitations

- Bulk/cascade delete, idempotent delete, optimistic locking, audit fields, ETags, conditional requests, authentication, authorization, and security-provider integration are future capabilities.
- Relationship modeling is not part of the current Application Model baseline.
- Advanced persistence options such as additional databases, entity graphs, Testcontainers, MapStruct, and P6Spy require explicit future decisions.
- Partial module selections may not produce independently runnable applications unless a specific quality gate validates that selection.
- Exact versions, current artifact counts, and measured dry-run state are intentionally not duplicated here; see [Current State](../project/CURRENT-STATE.md).
