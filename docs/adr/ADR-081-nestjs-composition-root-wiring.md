# ADR-081: NestJS Composition-Root Wiring

* Status: Accepted
* Date: 2026-08-11
* Milestone: 7.16

## Context

ADR-057 assigned dependency-injection wiring to the generated `bootstrap` module: "`bootstrap` —
application composition root wiring `infra-persistence` and `web-api` to `core` through dependency
injection." The implementation diverged from that assignment. The milestone 7.8 readiness audit
measured the divergence:

* The per-entity NestJS `@Module` was emitted by the `web-api` module at
  `src/web-api/entrypoints/<collection>/<entity>.module.ts` and imported
  `src/infra/providers/*` and `src/infra/repositories/*`, although the profile declares
  `web-api` as `requires: [core]`.
* The generated e2e specification was also emitted by the `web-api` module at
  `test/app.e2e-spec.ts` and imported `src/app.module`, a `bootstrap` artifact.

Both artifacts belong to `web-api` by declaration while depending on modules `web-api` does not
declare. The full profile hid the problem because `bootstrap` pulls in every module, but a
`--module web-api` selection emitted files whose imports were never generated: two unresolved
relative imports across the selection, so it could not compile on its own.

This is the NestJS counterpart of a boundary the Java Golden Path already enforces. ADR-015 keeps
explicit Spring wiring in the generated `configuration` module rather than in `entrypoints-rest`,
and generated ArchUnit rules (ADR-024, ADR-068) fail the build if a delivery module reaches into
persistence.

## Decision

Dependency-injection wiring and whole-application tests are owned by the `bootstrap` module.

* The per-entity `@Module` moves to the `bootstrap` module and is generated at
  `src/modules/<entity>.module.ts`, beside `src/app.module.ts`. Its template moves to
  `bootstrap/modules/module.ts.njk` and its template id becomes `bootstrap-entity-module`.
  Relative imports shorten from `../../../core/...` to `../core/...` and `../infra/...`, and the
  controller is imported across the layer boundary as `../web-api/entrypoints/<collection>/<entity>.controller`.
* `src/app.module.ts` imports each wiring module from `./modules/<entity>.module`.
* The generated e2e specification moves to the `bootstrap` module as `bootstrap-e2e-test`. Its
  output path, `test/app.e2e-spec.ts`, and its content are unchanged; only its owning module
  changes. `test/jest-e2e.json` stays with `build`, which owns tooling configuration rather than
  test code.

A composition-root directory is chosen over keeping the wiring co-located with the controller in
`src/web-api/entrypoints/<collection>/`. Feature-co-located modules are the more common NestJS
idiom, but co-location is what forced a delivery-layer artifact to import persistence. The Java
Golden Path already accepted the same trade-off under ADR-015, and consistency between Golden
Paths on where composition lives is worth more here than matching the framework's most common
file placement.

The profile manifest is deliberately not changed. Declaring `web-api` as
`requires: [core, infra-persistence]` would also have made the manifest consistent with the
generated imports, but it would have recorded the layering violation as intent rather than
removing it, and it would contradict the inward-dependency direction documented for this Golden
Path.

## Consequences

No generated artifact is added or removed: the full `examples/wallet-service` profile still emits
57 CREATE operations, and `build` (5), `core` (26), `infra-persistence` (32), and `bootstrap` (52)
selections are unchanged. The `web-api` selection drops from 44 to 42 CREATE operations, since two
artifacts it used to own are now generated by `bootstrap`.

Every relative import in the full profile and in the standalone `web-api` selection now resolves
within its own selection, so `--module web-api` is structurally complete rather than partially
generated. No generated `web-api` file imports `infra`, restoring the `web-api -> core` direction
this Golden Path documents.

Two generated file paths change for existing users of this profile, which is a breaking change to
generated output rather than to the generator's inputs. It is accepted at this point because the
Golden Path has no consumers yet beyond this repository's own golden fixtures, and because the
alternative is shipping the violation into the first release.

The move is enforced only by producer unit tests and golden byte comparison. No architecture-boundary
lint is generated for this Golden Path; an ArchUnit equivalent remains future optional work, so a
future milestone can reintroduce the same class of defect without a generated guardrail catching it.
